# Ползване без регистрация (гост)

Цел: човек отваря приложението и директно попълва данните си (пол, възраст…), натиска „Създай моя план“ и вижда плана — без имейл и парола. Вход/регистрация се предлага чак накрая, с Google или Facebook.

Подход: **анонимен акаунт в Supabase**. Гостът е нормален потребител за базата (същите таблици и RLS). При регистрация с Google/Facebook същият акаунт става постоянен (`linkIdentity`) — нищо не се прехвърля и не се губи.

> Firebase не е нужен: Supabase Auth поддържа Google и Facebook вход директно.

## Решения (обсъдени)

- [x] Гостът може всичко освен eBag: план, списък за пазаруване, рецепти, отметки.
- [x] Регистрацията е с бутони „Продължи с Google“ / „Продължи с Facebook“ (без имейл/парола за новите хора).
- [x] Гост-акаунтите се трият автоматично след **3 дни без активност**.
- [x] Защита от злоупотреба: лимитът на Supabase (30 гост-акаунта на час от IP); captcha само ако видим злоупотреба.
- [x] Първият екран е директно въпросникът (пол, възраст…); въпросът за вход е накрая.

## 1. Настройки на Supabase

- [x] `supabase/config.toml` (локално): анонимен вход, ръчно свързване, redirect URL-и за localhost, блокове за Google и Facebook (изключени, докато няма ключове в `supabase/.env`).
- [x] Dashboard (production + тестовия проект) → Authentication → Sign In / Providers: включи **Allow anonymous sign-ins** и **Allow manual linking**.
- [x] Google: OAuth клиент в Google Cloud Console (екран за съгласие, redirect URL към Supabase), Client ID/Secret в Supabase.
- [x] Facebook: приложение в Meta for Developers, App ID/Secret в Supabase. Внимание: за публично ползване Meta изисква App Review и бизнес верификация — може да отнеме дни/седмици. Предлагам Google първо, Facebook след това.
- [x] Dashboard → Authentication → URL Configuration: Site URL = production адресът; Redirect URLs: `https://<домейн>/**`, `http://localhost:3000/**` (и Vercel preview адресите, ако ще тестваш там).

## 2. Въпросникът без вход

- [x] Middleware: `/onboarding` и `/install` са достъпни без сесия; нелогнат потребител на `/` отива на `/onboarding`. По-дълбоки страници (`/plan` и т.н.) без сесия → `/login`. Гост може да отвори `/login`.
- [x] Въпросникът пази отговорите само в браузъра, докато се попълва — гост-акаунт **не** се създава при отваряне на страницата (иначе ботове и случайни посещения правят празни акаунти).
- [x] На последната стъпка („Създай моя план“): ако няма сесия → `signInAnonymously()` → запис на профила → създаване на плана → отваряне на `/plan`. Грешка 429 (лимитът) има отделен текст.
- [x] Бутонът „Изход“ на първата стъпка изчезва за нелогнати; вместо него линк „Имам акаунт — вход“.
- [x] Текстът за съгласие: за гости пише, че данните се пазят 3 дни и после се изтриват.
- [x] E2E тест `e2e/guest.spec.ts` (иска включен анонимен вход в тестовия Supabase проект).

## 3. Покана за регистрация

- [x] Карта на екрана с плана за гости: „Запази плана си“ + „Продължи с Google“; пише, че без вход планът изчезва след 3 дни (`components/SaveAccount.tsx`).
- [x] eBag екранът за гости: вместо „Свържи eBag“ — „Влез, за да изпратиш продуктите в eBag“. `/api/ebag/connect` връща гостите обратно (и на сървъра, не само в интерфейса).
- [x] Бутони „Продължи с Google“ / „Продължи с Facebook“ → `linkIdentity` за гост (акаунтът става постоянен, планът остава). Facebook бутонът се показва само с `NEXT_PUBLIC_AUTH_FACEBOOK=1` (след одобрението от Meta).
- [x] Ако този Google акаунт вече съществува (`identity_already_exists`): вход в съществуващия акаунт; профилът и последният план на госта се копират, ако акаунтът няма профил, иначе остават старите данни. Гостът се изтрива. ID-то на госта минава през криптирана бисквитка (`lib/auth/guestMerge.ts`).
- [x] Callback route `/auth/callback` — разменя кода за сесия и връща към страницата, от която е тръгнал, с „Готово — планът ти е запазен“ или грешка.
- [ ] Ръчна проверка с истински Google акаунт (нов акаунт и вече съществуващ) — не може да се автоматизира без Google.

## 4. Входният екран

- [x] `/login` вече не е начален екран (middleware праща новите хора на въпросите); остава за „Имам акаунт“.
- [x] Отгоре: „Продължи с Google“ (и Facebook с `NEXT_PUBLIC_AUTH_FACEBOOK=1`). Отдолу, след „или с имейл и парола“: старата форма за вход/регистрация. Най-долу: „Нямам акаунт — започни без регистрация“ → въпросите.
- [x] Логнат потребител (нормален) на `/login` → към `/` (→ плана). Гост на `/login` може да влезе в друг акаунт.
- [x] Гост, който влиза тук, запазва плана си: Google се свързва към него (както в раздел 3); вход или регистрация с имейл също пренасят данните му (`app/login/actions.ts`).

## 5. Изтриване на гост-акаунтите

- [ ] Ежедневна задача (pg_cron в Supabase или Vercel Cron към защитен API route), която трие от `auth.users` анонимните потребители без активност повече от 3 дни (`is_anonymous = true`, по последна активност, не по дата на създаване).
- [ ] Провери, че `on delete cascade` чисти профила, плановете и отметките; обратната връзка остава с `user_id = null` (вече е така).
- [ ] Лог на броя изтрити акаунти за всяко пускане.

## 6. Разлики гост / регистриран в кода

- [ ] Помощна функция `isGuest(user)` (`user.is_anonymous`) за сървъра и клиента.
- [ ] `/api/ebag/*`: гост получава ясна грешка (403 + текст „Влез, за да свържеш eBag“), не общата.
- [ ] Профил екранът за гост: вместо „Изтрий профила“ / имейл — поканата за регистрация; „Изтрий данните ми“ остава.
- [ ] Лимит на `/api/plan` за гости (напр. до 10 плана на ден), за да не се товари солвърът.

## 7. Тестове

- [ ] E2E: отваряне без вход → въпросник → план → списък (без нито един имейл).
- [ ] E2E: гост → „Продължи с Google“ (mock на OAuth) → планът е още там.
- [ ] RLS тест: гост вижда само своите данни, както нормален потребител.
- [ ] Тест на задачата за изтриване: стар гост се трие, нов гост и нормален потребител остават.
- [ ] Преводи (bg + en) за всички нови текстове.
